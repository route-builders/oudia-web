# テスト規約

本プロジェクトのテストの書き方・配置・運用ルールを定める。テスト戦略の全体像は [design/02_architecture.md](./design/02_architecture.md) §7、フィクスチャの整備は [design/08_test-fixtures.md](./design/08_test-fixtures.md) を正とする。

## 1. テストの種類と配置

| 種類                       | ツール              | 対象パッケージ           | 目的                                                                                                  |
| -------------------------- | ------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------- |
| **黄金テスト(バイト一致)** | Vitest (Node)       | format                   | 実ファイル「読込 → 書出 → バイト一致」。**CI 必須ゲート**                                             |
| ユニットテスト             | Vitest (Node)       | format / domain / derive | 関数・レデューサ単体の仕様検証                                                                        |
| プロパティベーステスト     | Vitest + fast-check | domain                   | 整合カスケードの不変条件(任意の駅追加削除・種別入替後に「全列車の駅時刻数 = 駅数」等)                 |
| スナップショットテスト     | Vitest              | derive / render          | レイアウト座標・cellSpec・描画コマンド列の回帰検知                                                    |
| 比較テスト(移植先行)       | Vitest              | derive                   | 運用探索: Windows 版と同一入力 → 同一出力(移植**前に**用意する)                                       |
| ベンチマーク               | Vitest bench        | format / render          | 性能予算([design/04](./design/04_file-io.md) §10、[design/06](./design/06_rendering.md) §3)の回帰検知 |
| E2E                        | Playwright          | apps/web                 | キーボード操作・ファイル開閉・クラッシュ復元(v0.4 で本格整備)                                         |

配置はテスト対象の隣(`src/**/*.test.ts`)。フィクスチャは `fixtures/` に置き、design/08 の台帳で管理する。

## 2. 黄金テスト(最重要ルール)

- 対象: `sample.oud2`、`sample2.oud2` + 自作フィクスチャ群(番線・分岐環状・運用・カスタマイズ時刻表を含む)
- 判定: **バイト列の完全一致**。ただし `FileTypeAppComment` 行のみ正規化して比較し、別途「元値注入で完全一致」も検証する(design/04 §4.4)
- **黄金テストが fail する変更はマージ禁止**。例外なし
- format の挙動を意図的に変える場合は、期待値の更新理由を PR に明記し、Windows 版での検証結果を添える
- 新しい互換性バグを直したら、そのケースを再現する最小フィクスチャを必ず追加する

## 3. テストの書き方

### 命名・構造

- `describe` / `it` の記述は日本語でよい。**仕様が読み取れる文**にする:
  ```ts
  describe('compareJikoku', () => {
    it('24時間サイクリック比較で 23:59 と 0:01 の差を +2分 と判定する', () => { ... })
  })
  ```
- Arrange-Act-Assert パターンに従い、1 テスト 1 検証事項を基本とする
- テストデータの構築はフィクスチャまたはビルダー関数に寄せ、テスト本文では差分だけを書く

### 原典準拠テスト

原典の挙動を検証するテストには、根拠(分析ドキュメントの節番号または原典ソースパス)をコメントで付ける:

```ts
// 根拠: docs/analysis/02_domain-model.md §6(CdDedJikan の循環比較)
// 原典: entDed/CdDedJikoku.cpp
```

### プロパティベーステスト

- domain の整合カスケード(駅・種別・番線の増減、index 再マップ)には fast-check の常設プロパティテストを置く(roadmap M5 完了条件)
- 不変条件は design/03 §8(整合性ルール)から選ぶ。テスト名に不変条件を明記する
- 失敗時の再現シードをテストファイルにコメントで固定できるようにする

### スナップショットテスト

- スナップショットの更新(`--update`)は、**差分が意図した変更のみであることを確認してから**行う。PR に差分の説明を書く
- 巨大スナップショットは避け、代表ケース + 境界ケース(60 秒閾値、日跨ぎ、経由なし)に絞る

## 4. カバレッジ方針

数値ノルマは設けないが、層ごとの期待水準を定める:

| パッケージ | 期待水準                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| format     | 高(すべての分岐が互換性に直結)。世代別リーダーは全世代フィクスチャで実行される状態を保つ |
| domain     | 高。全コマンドレデューサにテスト、カスケードはプロパティテスト                           |
| derive     | 中〜高。純関数はスナップショット + 境界ケース                                            |
| render     | スナップショットによる回帰検知のみ(厳密一致は求めない)                                   |
| apps/web   | E2E で主要フローをカバー。コンポーネント単体テストは複雑なロジックを持つ場合のみ         |

## 5. CI ゲート

PR マージには以下すべての green を要求する(GitHub Actions):

1. `pnpm typecheck`
2. `pnpm lint`(ESLint + dependency-cruiser)
3. `pnpm format:check`
4. `pnpm test`(ユニット + 黄金テスト + プロパティテスト)
5. ライセンスチェック(GPLv3 非互換依存の混入防止)
6. ベンチマーク記録(前回比 +30% で警告、+100% で fail。design/04 §10)
7. E2E(整備後。UI に影響する PR のみ必須)

## 6. テストを書かなくてよいもの

- Spike の使い捨てコード
- 型定義のみのファイル
- 設定ファイル

ただし Spike から恒久コードに昇格させる時点で通常の基準を適用する。
