# テストフィクスチャ調達計画

本書は、互換戦略の全テスト(黄金テスト CI ゲート、旧世代 → 1.17 変換の期待値比較、運用探索比較テスト)が依存する**テストフィクスチャの調達・生成・管理計画**である。`docs/design/02_architecture.md` §7(テスト戦略)、`docs/design/04_file-io.md` §5(ラウンドトリップ保証のテスト設計)、`docs/design/07_roadmap.md` M0「フィクスチャ環境」・M7a を具体化する。

## 0. 問題設定 — なぜ調達「計画」が必要か

互換テストの前提には次の構造的な制約がある。

1. **現行 Windows 版(ver2.06.23)は常に最新 FileType(OuDiaSecond.1.17)と .oud(OuDia.1.02)でしか保存できない**(分析 §03、file-io §1.2-2)。つまり ver2.06.23 だけをいくら操作しても、旧世代 oud2(1.00〜1.16)のテスト入力は 1 バイトも作れない。
2. ロードマップは旧世代フィクスチャを **M1 の完了条件**(1.00/1.05/1.09/1.10/1.16/OuDia.1.02 が全て開ける)と **M2 の完了条件**(旧世代 → 1.17 変換の期待値一致)に組み込んでいる。フィクスチャが無ければ M1 から先が検収不能になる。
3. **M7a は「Windows 版と同一入力 → 同一 OperationTableContent」の入出力ペア 30 本以上**を移植前に要求するが、OperationTableContent は導出値でありファイルに保存されない。機械可読で取り出す手段を別途確立する必要がある。

本書はこれらを「入手(§1)→ 生成(§2)→ 台帳管理(§3)→ 外部受入(§4)→ 運用探索ペア採取(§5)」の 5 手順として確定する。

### 1.2 入手経路の調査結果(2026-07 時点)

- **OuDiaSecond 公式ブログ**(<https://oudiasecond.seesaa.net/>)は版ごとのリリース記事を残しており、各記事に Seesaa 添付ストレージ(`oudiasecond.up.seesaa.net/image/…`)のダウンロードリンクがある。**Ver2.04.01 の記事で「インストーラ zip + ソース zip」のリンクが現存することを実確認した**(<http://oudiasecond.seesaa.net/article/474782440.html>: `oudiasecond.2.04.01.zip` / `OuDiaSecond_2.04.01.src.zip`)。Ver2.01・Ver2.05 系・Ver2.06 系の各記事も存在する。**Ver2.x 系(FileType 1.06〜1.16)は公式ブログ経由で入手可能と判断する。**
- **Ver1.x 系(2017〜2019、FileType 1.00〜1.05)**はブログ初期記事(「OuDiaSecondとは」2017 年 <http://oudiasecond.seesaa.net/article/448892855.html> 等)に添付されていた可能性が高いが、リンクの生存は未確認。M0 でブログアーカイブ(月別記事一覧)と Wayback Machine(web.archive.org)を走査して確認する。**入手できない前提の代替手順(§2.3 synthetic)を既定計画とし、入手できたら実バイナリ生成に差し替える**(M0 をブロックしない)。
- **本家 OuDia**(take-okm 氏、<http://take-okm.a.la9.jp/oudia/index.html>)は Ver1.02.05 が公式サイトおよび Vector で配布継続中。実 .oud フィクスチャ(OuDiaSecond を経由しない「本物の OuDia が書いた .oud」)の生成に使う。
- 各版とも Windows 11 上でサイドバイサイドにインストール可能(インストーラ版はインストール先を版ごとに変える。ソース zip からのビルドでも可)。実行環境はロードマップ M0 の「Windows 実機 or VM」を共用する。

### 1.3 アーカイブ方針(確定)

1. **歴代バイナリ(インストーラ zip・ソース zip)はリポジトリに同梱しない。** 理由: (a) GPLv3 のバイナリ頒布には対応ソースの提供義務が随伴し、他者の版のソース提供責任を本リポジトリが負うことになる(各版のソース zip も併せて保全すれば法的には可能だが、管理コストに見合わない)、(b) リポジトリ肥大。
2. 代わりに、入手した zip は**開発者のプライベートアーカイブ**(ローカル + クラウドの 2 重)に版番号・入手元 URL・入手日とともに保全し、**SHA-256 をフィクスチャ台帳(§3.3)に記録**する。台帳のハッシュにより「どのバイナリでフィクスチャを生成したか」を第三者が(バイナリを別途入手すれば)検証できる。
3. 保険として、各リリース記事 URL と添付 zip URL を **Wayback Machine に保存リクエスト**しておく(M0 の 1 作業。公的アーカイブへの保存依頼であり本プロジェクトによる頒布ではない)。配布元ブログの消滅が最大の入手リスクであり、これが最も安価な軽減策。
4. 歴代バイナリで**生成した oud2/oud ファイル(フィクスチャ)自体は本プロジェクトの著作物**としてリポジトリにコミットする(路線名・駅名等は架空のものを入力する)。バイナリ非同梱とフィクスチャ同梱は矛盾しない。

### 2.2 実バイナリでの生成手順(共通シナリオ方式)

世代間の比較可能性のため、**全世代共通の入力シナリオ台本**を 1 つ定義し、各版でそれを再生して保存する。

1. 台本は `packages/format/fixtures/README.md` に手順書として書く(例: 「駅 8 駅(うち同名駅 2 回登場の分岐 1 箇所)、種別 3、ダイヤ 2(平日/休日)、下り 12 本・上り 10 本、うち日跨ぎ 2 本・秒付き 3 本・通過主体 2 本…」)。その版に存在しない機能(例: Ver1.00 に番線 UI はあるが交差支障はない)は台本の該当節をスキップする。
2. 各版で台本を入力 → その版の既定形式で保存 → ファイル先頭の `FileType=` が期待世代であることを確認してコミット。
3. 同じファイルを**現行 ver2.06.23 で開いて 1.17 保存**したものを `*.expected.oud2` としてペアでコミット(M2 T2 の右辺)。
4. 操作した版番号・日付・スキップした節を台帳(§3.3)に記録する。

補助として、**より新しい世代のファイルはより古い世代のファイルを包含しない**点に注意する(1.16 のフィクスチャがあっても 1.10 リーダーの「1.11 以降キーの欠落デフォルト」経路は踏めない)。マトリクスの必須 5 世代はこの経路網羅から決めている(§1.1 右列)。

### 2.3 synthetic フィクスチャの作成手順(v100 / v105 の既定計画)

実バイナリなしで旧世代ファイルを用意する手順。**正当性の根拠を「原典リーダーが受理し、原典が期待通りの 1.17 に変換すること」に置く**(仕様書の自己言及にしない)。

1. 分析 §03 §7(世代差分: S00 は `$番線` なし・Kyoukaisen あり・駅扱 3 あり、S05 は `RessyaTrack`/`OperationNumber` 別キー等)に従い、§2.2 と同じ台本内容を手書きで oud2 化する。文字コード・改行は世代仕様(UTF-8+BOM+CRLF)どおり。
2. 作成中の参照実装として原典ソースの該当リーダー(`origin/.../entDed/CconvCentDedS00.cpp` / `S05.cpp`)を読み、**「原典が読むキーだけを書く」**(原典が読まないキーを書いても検証にならないため)。
3. §2.4 の 3 条件で検証し、合格したものだけをコミットする。台帳の生成方法欄は `synthetic(手書き、分析§03§7 準拠、ver2.06.23 で検証済み)` とする。
4. 後日実バイナリが入手できたら、同じ台本で実生成したファイルを**追加**する(synthetic は削除しない — 手書きゆえに含まれる境界表現も資産)。

### 2.4 旧世代フィクスチャの合格 3 条件(実生成・synthetic 共通)

1. **現行 Windows 版 ver2.06.23 でエラー・警告なしに開ける**(原典リーダーによる受理 = 世代文法として正しいことの実証)。
2. **現行 Windows 版で「開く → 1.17 保存」した出力(= `*.expected.oud2`)が、意図した内容(台本)を過不足なく含む**(目視 + 現行版画面での時刻表/ダイヤグラム確認)。
3. Web 版実装後: **Web 版の「旧世代読込 → 1.17 書出」が `*.expected.oud2` と一致する**(M2 T2。FileTypeAppComment 行は正規化)。

条件 1・2 は M0 で(Web 版コードなしで)完了できる。**M0 完了条件の「フィクスチャの入手・作成・検証手順のドキュメント化」= 本書 + 条件 1・2 済みフィクスチャ一式のコミット**、と読み替えて確定する。

## 3. コーパス台帳

### 3.1 配置規約

file-io §5.1 の構成を正とし、次のとおり拡張する。

```
packages/format/fixtures/
├── README.md                 # 台帳(§3.3)+ 生成台本(§2.2)+ 期待値生成手順
├── current/                  # 1.17 実ファイル(T1 対象)
├── legacy/
│   ├── v100/ v105/ v109/ v110/ v116/   # 各 *.oud2 + *.expected.oud2
│   └── oud/                            # *.oud + *.expected.oud2(読込変換期待値)
├── synthetic/                # 境界ケース(escape / sjis-0x5c / unknown-keys / edge-jikoku …)
└── oud-export/               # .oud 書き出し期待値(T6)
packages/derive/fixtures/
└── operation/                # M7a 運用探索入出力ペア(§5)
    └── case01/ … case30+/   # input.oud2 + expected.operation.json(+ 採取メタ)
```

- **origin/ 同梱の sample.oud2 / sample2.oud2 は fixtures/ に複製しない。** テストは `origin/DiagramEdit/manual/` のパスを直接参照する。理由: file-io §5.1 の注記どおりサンプルのライセンス帰属(GPLv3 か GFDL か)が未確定であり、確定までは「原典アーカイブの一部としてそのまま置かれている」状態を変えない。帰属が GPLv3 と確定したら current/ へ複製してよい(それまでも参照テストは可能なので実害はない)。
- fixtures はすべてバイナリ完全一致が意味を持つため、`.gitattributes` で該当拡張子を `-text`(改行変換禁止)に指定する。**CRLF を Git に触らせない**こと。エディタの自動整形(final newline 付加等)も `.editorconfig` で除外する。

## 4. ユーザ提供ファイルの受入手順

互換セルフチェック(アーキ §6.4)の差分レポートは匿名化済みでそのまま使えるが、**実ファイルをコーパスにコミットする**場合は次の手順を踏む。

1. **許諾**: 提供者から次の文面への明示同意(issue または メール)を得て、同意記録の URL/日付を台帳に記す。
   > 提供するファイルについて、(1) 自分が作成した(または権利者の許可を得た)こと、(2) 本プロジェクト(GPLv3 で公開されるリポジトリ)のテストデータとして同梱・再配布されること、(3) 将来の削除依頼には応じるが過去リリースからの遡及除去は保証されないこと、に同意します。
2. **内容確認**: 実在ダイヤの丸写しは事業者の権利関係が不明瞭になり得るため、受入時に確認し、懸念があれば §4-3 の匿名化を必須とする(判断基準: 事業者名・実在列車名がそのまま入っているか)。
3. **匿名化(任意/条件付き必須)**: 駅名・列車名・種別名・備考・コメントを機械置換する小ツール(`tools/fixtures/anonymize.ts`、format パッケージのパーサを利用)を用意する。置換後もラウンドトリップ性は保たれるためフィクスチャ価値は残るが、**バイト列依存の不具合(0x5C 文字・エスケープ等)は置換で消え得る**。したがって「差分を再現する最小 synthetic を先に起こし、匿名化ファイルは補助として入れる」を原則とする。
4. **受入テスト**: コミット前に T1(1.17 の場合)または条件 1・2(旧世代の場合)を通す。通らないファイルこそ価値があるので、原因をキーパスまで特定し、修正 or 新規則の synthetic 化とセットでコミットする。

## 5. M7a: 運用探索入出力ペアの採取方法

OperationTableContent・割当運番はファイルに保存されない導出値のため、Windows 版から機械可読で取り出す経路を 2 系統確定する。

### 5.1 主経路: 原典ソースの計測ビルド(instrumented build)

原典ソース一式が `origin/` にある(VS2019 Community でビルド可能、`origin/ReadMe.txt`)ことを利用し、**ダンプ機能を足した検証専用ビルド**を作る。

- 改造内容: 起動引数 `/dumpoperation <入力.oud2> <出力ディレクトリ>` を追加。ファイル読込 → 各ダイヤで `CentDedRosen::OperationConnect(diaIndex)` 実行 → 次を UTF-8 JSON で出力して即終了する。
  1. `CentDedDia::m_contOperationTableContent`(運番 → OperationTableContent リスト: 列車参照(方向, RessyaIndex)・開始/終了作業の種別と駅 Order・接続時刻)
  2. 全列車・全駅時刻・全作業の**導出スロット値**(割当運番、接続時刻・接続方向等の ※印フィールド。分析 §07)
  3. `InOutLinkCodeContent` の map(コード → iStatus・入区側/出区側列車群)
  4. `CustomizeJikokuhyouContent`(併合/分割チェーン)
- JSON のキー順・配列順はコンテナ格納順をそのまま書く(正規化しない)。**同一入力で 2 回実行して出力が一致することを確認**し、OpenMP 並列による非決定性がないことを各ケースで検証する(不一致が出たケースはシリアル実行(`omp_set_num_threads(1)`)に固定して採取し、その旨を台帳に記録)。
- 改造は最小 diff とし、**パッチファイルとしてリポジトリにコミットする**(`tools/oudia-win-harness/operation-dump.patch` + ビルド・実行手順 README)。origin/ 自体は改変しない。パッチも GPLv3 派生物であり本リポジトリのライセンスと整合する。
- Web 版側は同じ JSON スキーマで導出キャッシュをシリアライズする比較器を derive のテストに置き、`expected.operation.json` と deep-equal 比較する(これが M7 恒久ゲートの実体)。

### 5.2 副経路: UI の CSV エクスポート(クロスチェック用)

計測ビルドが何らかの理由で失敗する場合の保険、および計測ビルド自体の正しさの突き合わせに、原典 UI の機械可読出力を使う。

- 運用一覧表ビューの CSV エクスポート(抽出条件付き)と運用表 CSV(`CconvOperationTableCsv`)は、割当運番・出入区駅/時刻・列車列を表形式で含む(分析 §07)。代表 5 ケースについて CSV も採取し、計測ビルドの JSON から同じ CSV を再構成できることを確認する(表示文字列化で情報が落ちるため、主経路の代替ではなくクロスチェックに留める)。
