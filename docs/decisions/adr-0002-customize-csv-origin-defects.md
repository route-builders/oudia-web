# ADR-0002: カスタマイズ時刻表 CSV は原典の欠陥を修正して実装する

## ステータス

Accepted

## コンテキスト

follow-up #11(カスタマイズ時刻表)の CSV 出力を移植するにあたり、原典
`origin/DiagramEdit/DiagramEdit/ConvJikokuhyouCsv/CconvJikokuhyouCustomizeCsv.cpp`
を精読したところ、**そのままでは移植の基準にできない欠陥**が見つかった。

本プロジェクトの原則は「原典に忠実移植とし、独自再設計しない」(CLAUDE.md /
design §4.6)であり、実際これまで原典のバグも意図的に再現してきた
(例: 運用表 CSV エクスポートの照合方法コンボはラベルと実装が入れ替わっているが、
Windows 版と抽出結果を揃えるためそのまま移植した)。

しかし今回は前提が違う。

### 欠陥 1: そもそもコンパイルできない(致命的)

`_T("+";)` が 6 箇所(:386, :394, :3182, :3190, :4739, :4747)、`_T("↓";)` が 2 箇所
(:3202, :4759)。意図は `_T("+");` / `_T("↓");`。
このファイルは `DiagramEdit.vcxproj:242` に `ExcludedFromBuild` なしで登録されているため、
**配布ソースはこのファイルを含めてビルドできない**。

つまり「原典の実際の挙動」を観測する手段が、配布ソースの範囲には存在しない。
忠実移植の基準となる *振る舞い* が定義されていない。

### 欠陥 2: 出力が壊れるバグが 3 件

いずれも「有効にすると CSV の列がずれる / ラベルが出ない」もので、
ユーザーが設定を変えると破綻する。

1. `encode()` の EkiRessyamei / EkiPrevRessyamei 分岐(:5626-5642, :5700-5720)が
   ヘッダの 2・3 行目を `aRow2` / `aRow3` ではなく `aRow` に insert している。
   `CdCsvRow` は値コピー後なので、実際に文書へ入るのは**セル 0 個の空行**。
   号数・号のヘッダラベルが出力されない。
2. `encode_AddRessya` :4983 が `ColumnType_EkiRessyamei` の**二重分岐**で、
   :3516 で既に処理済みのため到達不能。本来は `ColumnType_EkiPrevRessyamei`。
   結果、[前の列車名を表示] を有効にすると **ヘッダは 3 行出るのにデータセルが 0 個**
   となり、それ以降の全行が列ズレする。
3. `encode_AddRessyaNull`(:5174-5181)が運用番号を `iOperationNumberRows` に関係なく
   **1 行しか出さない**。`operationNumberRows >= 2` かつ空列があると以降が (rows-1) 段ずれる。
   ★これは通常時刻表 CSV(`CconvJikokuhyouCsv.cpp:2541-2548`)にも同じバグがある。

### 欠陥 3: ラベル文字列の取り違え(通常 CSV と共通)

`DiagramEdit.cpp:746-772` が `nameShihatsuEkimei` 引数に `IDS_WORD_ShuchakuEkimei` を
渡しているため、「始発駅名」ヘッダ行は実際には **"終着駅"** と出力される
(`DiagramEdit.rc:3436-3437` で ShihatsuEkimei="始発駅" / ShuchakuEkimei="終着駅")。
通常 CSV(`DiagramEdit.cpp:736`)も同じ。既存の
`packages/derive/src/csv/timetableCsv.ts:52` は '始発駅' を出しており、既に原典と乖離している。

## 決定

**カスタマイズ時刻表 CSV は「作者が意図した動作」を実装する。** 具体的には:

- 欠陥 1(構文誤り)は、コメント・周辺コードから読み取れる意図
  (`_T("+")` / `_T("↓")`)で解釈する。
- 欠陥 2 の 3 件は**修正して実装する**(ヘッダ行を正しい row へ、EkiPrevRessyamei の
  データセルを出す、運用番号を段数ぶん出す)。
- 欠陥 3 のラベル取り違えは**修正して "始発駅" を出す**。既存 `timetableCsv.ts` の
  挙動に合わせ、通常 CSV との一貫性を優先する。

そのうえで、**修正した各点をコード内コメントに `★原典バグを修正` として file:line 付きで
明記**し、テストで固定する。

## 検討した選択肢

### 選択肢 1: 完全な忠実移植 ❌

- **説明**: 構文誤りを意図解釈で埋めたうえ、欠陥 2・3 もそのまま再現する。
- **メリット**: 「原典と同一出力」という判定基準が一応保てる。
- **デメリット**:
  - 比較対象の実行ファイルが**存在しない**(ビルド不能)ので、忠実かどうかを検証できない。
  - 列ズレした CSV は表計算で開くと壊れて見える。ユーザーから見れば単なる不具合。
  - 欠陥 3 を再現すると、既存の通常時刻表 CSV(すでに "始発駅" を出している)と
    プロジェクト内で不整合になる。
- **評価**: 検証不能な「忠実さ」のために壊れた出力を作ることになるため不採用。

### 選択肢 2: バグ修正版を実装し ADR に記録する ✅

- **説明**: 上記「決定」のとおり。
- **メリット**:
  - 出力が壊れない。表計算にそのまま読ませられる。
  - プロジェクト内(通常 CSV とカスタマイズ CSV)で一貫する。
  - 差分が ADR + コードコメント + テストで追跡できる。
- **デメリット**: Windows 版と CSV がバイト単位で一致しなくなる。
  → **軽減策**: そもそも Windows 版はこのファイルをビルドできず、
  カスタマイズ CSV に decode(再取込)も存在しないため、往復・相互運用の要件がない。
  影響は「人が読む CSV の見た目」に閉じる。
- **評価**: 採用。

### 選択肢 3: カスタマイズ CSV を実装しない ❌

- **説明**: グリッド表示だけ提供し、CSV は対象外にする。
- **メリット**: 判断が不要。
- **デメリット**: roadmap M6 の「カスタマイズ時刻表 CSV」が未達のまま残る。
- **評価**: 機能として求められているので不採用。ただし優先度は最後でよい。

## 影響

- **ポジティブ**: カスタマイズ CSV が実用的な出力になる。通常 CSV との一貫性が保てる。
- **ネガティブ**: Windows 版との CSV バイト一致が保証できない
  → 軽減策は上記のとおり(往復要件なし・decode なし・ビルド不能)。
- **影響を受けるドキュメント/コード**:
  - `packages/derive/src/csv/`(カスタマイズ CSV の新規実装)
  - `packages/derive/src/csv/timetableCsv.ts`(欠陥 3 の扱いを合わせる。現状維持)
  - `docs/design/07_roadmap.md` の M6 スコープ注記

## 検証方法・見直し条件

- 成功基準:
  - すべての表示設定の組み合わせで**列数がヘッダとデータで一致**する
    (欠陥 2 の 3 件が再発しないことをテストで固定)。
  - 修正点がコード内で `★原典バグを修正` + file:line で辿れる。
- 見直し条件:
  - 原典の将来版でこれらの欠陥が修正され、**修正後の挙動が本 ADR の解釈と違った**場合。
    その時は原典に合わせ直し、本 ADR を Superseded にする。
  - 実機(Windows 版)でカスタマイズ CSV を出力できる手段が見つかり、
    実際の出力が観測できるようになった場合。
