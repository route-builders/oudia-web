# ADR-0001: Web 再実装アーキテクチャの基本方針

## ステータス

Accepted

## コンテキスト

OuDiaSecond(C++/MFC、Windows 専用)をブラウザで動く Web アプリとして再実装するにあたり、技術スタック・レンダリング方式・状態管理・ファイル I/O 方式の基本方針を決める必要があった。前提条件は [design/01_goals-scope.md](../design/01_goals-scope.md) のとおり(.oud2 バイト互換必須、クライアント完結、オフライン動作、GPLv3、個人開発での段階リリース)。

決定は、3 方針(互換性最優先 / モダン Web 最優先 / 段階リリース最優先)の独立提案と審査による比較検討を経て、統合案として確定した。詳細な検討経緯と決定内容は [design/02_architecture.md](../design/02_architecture.md) §2 に記録されている。

## 決定

以下を基本方針として採用する(詳細は design/02 が正):

1. **スタック**: TypeScript strict + React 18 + Vite + Zustand/Immer(produceWithPatches)+ Comlink + vite-plugin-pwa。pnpm workspaces
2. **モジュール構成**: `format ← domain ← derive ← render ← app` の一方向依存(lint で強制)
3. **レンダリング**: ダイヤグラム・時刻表グリッドとも Canvas 2D(ダイヤグラムは 4 レイヤ構成、原典 entDgr の忠実移植)。WebGL・DOM 仮想化グリッドは不採用
4. **状態管理と Undo/Redo**: `executeCommand()` 単一チョークポイント + Immer patch 方式の履歴
5. **ファイル I/O**: テーブル駆動の oud2 リーダー/ライター(世代別 4 系統)、未知キー保全、「読込 → 無編集 → 書出 → バイト一致」を CI 必須ゲート化
6. **配布**: 完全オフライン PWA、サーバ不要、GPLv3 で公開

## 検討した選択肢

design/02 §2 参照(案1: 互換性最優先 / 案2: モダン Web 最優先 / 案3: 段階リリース最優先 の 3 案比較と統合)。採用案は「案3 の段階リリース構成を基盤に、案1 の互換規律(バイト一致・原典忠実移植)と案2 の内部品質(層分離・純関数化)を統合」したもの。

## 影響

- **ポジティブ**: 互換性リスクの早期解消(M0 スパイクで実証)、各リリースが単独で価値を持つ、DOM 非依存層の高速なテスト回転
- **ネガティブ**: Canvas 自前実装の初期コスト(UI ライブラリ・グリッドライブラリに頼らない)→ M0 スパイク S2/S3 で性能と実装可否を先に検証して軽減
- **影響を受けるドキュメント**: docs/design/ 全体、[coding-standards.md](../coding-standards.md)

## 検証方法・見直し条件

- 成功基準: M0 スパイク S1〜S3 の合格([design/07_roadmap.md](../design/07_roadmap.md) §2)
- 見直し条件: スパイク不合格時は roadmap §2 記載の代替案(Path2D キャッシュ等)を先に適用し、それでも不成立の場合のみ本 ADR を再検討する
