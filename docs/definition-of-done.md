# 完了の定義 (Definition of Done)

タスクが「完了」とみなされるための基準を定義する。すべての PR はマージ前にこの基準を満たすこと。

## 目的

- 品質基準の明確化と、リリース可能な状態の維持
- **oud2 互換性(バイト一致)の恒久的な保証** — 本プロジェクトの生命線
- 技術的負債の蓄積防止

## 基本的な完了基準(全タスク共通)

### 1. コード品質

- [ ] `pnpm typecheck` がエラー 0 件(TypeScript strict、`exactOptionalPropertyTypes`)
- [ ] `pnpm check:code` がエラー 0 件(ESLint + 依存方向チェック)
- [ ] `pnpm format:check` が通過(Prettier 適用済み)
- [ ] [コーディング規約](./coding-standards.md)に準拠(命名、層の責務、SPDX ヘッダ)
- [ ] コードレビュー指摘事項に対応済み

### 2. テスト

- [ ] 新規・変更したロジックにテストがある([テスト規約](./testing-guidelines.md))
- [ ] `pnpm test` が全件 green
- [ ] **黄金テスト(バイト一致)が green** — M2 以降は恒久的なマージ条件。1 件でも fail していたら他の何が良くてもマージ不可
- [ ] エッジケース(null 時刻、経由なし、日跨ぎ、環状線・分岐駅など、ドメイン固有の境界)を考慮した

### 3. 互換性

- [ ] `.oud2` の読み書きに影響する変更の場合、ラウンドトリップ(読込 → 書出 → バイト一致)が維持されている
- [ ] 未知キー・未知ノードの保全([design/04_file-io.md](./design/04_file-io.md) §3)を壊していない
- [ ] 原典の挙動を変える場合、その差異が意図的であることをタスクドキュメントまたは ADR に記録した

### 4. ドキュメント

- [ ] 設計と実装が乖離した場合、`docs/design/` の該当ドキュメントを更新した
- [ ] アーキテクチャレベルの決定変更は ADR を作成した([decisions/README.md](./decisions/README.md))
- [ ] タスクドキュメントのステータス・進捗記録を更新した

### 5. ライセンス

- [ ] 新規ソースファイルに SPDX ヘッダがある(`// SPDX-License-Identifier: GPL-3.0-or-later`)
- [ ] 新規依存パッケージは GPLv3 互換ライセンスであることを確認した(MIT / BSD / Apache-2.0 等。CI のライセンスチェックが green)

### 6. バージョン管理

- [ ] ブランチ名・コミットメッセージが[規約](./tasking.md)に従っている
- [ ] コミットが論理的に分割されている
- [ ] PR テンプレートに従って記述し、関連タスク/Issue をリンクした
- [ ] CI がすべて green

## タスクタイプ別の追加基準

### Feature(機能開発)

- [ ] 対応するロードマップのマイルストーン機能一覧([design/07_roadmap.md](./design/07_roadmap.md))と突き合わせ、実装範囲を明記した
- [ ] 原典の挙動を再現する機能は、`docs/analysis/` の該当節(またはソース `origin/`)を根拠として実装した
- [ ] UI 機能はキーボード操作([design/05_ui-views.md](./design/05_ui-views.md) §4)を含めて実装した

### Bug(バグ修正)

- [ ] 根本原因を特定し、タスクドキュメント/PR に記録した
- [ ] 再発防止のテスト(その バグで fail するテスト)を追加した
- [ ] 同種のバグが他の箇所にないか確認した
- [ ] 互換性バグ(バイト不一致・原典と異なる挙動)の場合、該当ケースをフィクスチャとして追加した

### Refactor(リファクタリング)

- [ ] 既存テストがすべて green(挙動が変わっていないことの証明)
- [ ] 黄金テスト・スナップショットに差分がない(差分が出る場合はリファクタリングではない)
- [ ] ベンチマーク(該当パッケージにある場合)が悪化していない

### Spike(技術検証)

- [ ] 検証内容・合格条件・結果をタスクドキュメントに記録した
- [ ] 合否と、失敗時の代替案の適用判断を記録した
- [ ] 使い捨てコードは `spikes/` 等に隔離するか削除した(恒久コードに昇格させる場合は通常の基準を満たす)

### 描画系の変更(render / ダイヤグラム / 時刻表グリッド)

- [ ] Canvas スナップショットの差分が意図した変更のみであることを PR で説明した
- [ ] 500 列車 × 50 駅ベンチ([design/06_rendering.md](./design/06_rendering.md) §3)のフレーム予算を悪化させていない

### format パッケージの変更

- [ ] 全世代フィクスチャ(1.00〜1.17、OuDia.1.02)の読込テストが green
- [ ] 書き出しに影響する場合、キー出力順・改行・BOM・エスケープの一致を黄金テストで確認した
- [ ] エラーコード体系([design/04_file-io.md](./design/04_file-io.md) §3.7)との整合を維持した

## 品質ゲート(マージ条件のフロー)

```
実装 → typecheck/lint/format → ユニットテスト → 黄金テスト(バイト一致)
   → ライセンスチェック → コードレビュー → (UI変更時) E2E/手動確認 → マージ
```

いずれかが fail した場合は修正して再実行する。**黄金テストの fail を「あとで直す」ことは認めない。**

## 例外

以下の場合、チェック項目の一部を緩和できる。ただし PR に緩和した項目と理由を明記すること:

- **Spike**: テスト・ドキュメント要件を免除(使い捨て前提のため)
- **Docs / Chore**: コード関連の項目は該当なし
- **緊急のホットフィックス**: 事後に完全な対応を行うタスクを起票する

完了基準を満たせないまま何かをマージする場合は、技術的負債として GitHub Issue に記録し、対応タスクを作る。
